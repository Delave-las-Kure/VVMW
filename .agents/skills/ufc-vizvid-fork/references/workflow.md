# Работа с форком UFC VizVid

Порядок подготовлен 12 Nov 2026 по запросу владельца. Основная ветка нашего
форка — `ufc/cinema-stable`. Слово «мейн» в задачах владельца означает её.

## Репозитории и ветки

| Имя | Назначение |
|---|---|
| `origin` | Наш форк `Delave-las-Kure/VVMW`: сюда отправляем свои ветки и принятые изменения. |
| `upstream` | Оригинальный `JLChnToZ/VVMW`: получаем изменения; свои коммиты сюда не отправляем. |
| `ufc/cinema-stable` | Единственная основная ветка интеграции принятых изменений UFC. |
| `codex/fix-<task>`, `codex/feat-<task>`, `codex/docs-<task>` | Одна связная задача: исправление, функция или документация. |
| `codex/upstream-<version>` | Слияние конкретного релиза upstream с текущим UFC. |
| `codex/release-<version>` | Подготовка версии и метаданных пакета перед выпуском. |

Буквальная ветка `main` — историческая, вторую production-линию в ней не ведём.
Существующие `ufc/video-mirrors` и `ufc/playback-speed-binding` сохраняют свою
историю, но не служат общей базой новых задач. Ветки и worktrees автоматически
не удаляем. Отдельная постоянная ветка `develop` нашего форка не нужна.

## Начало задачи

1. Прочитать `AGENTS.md`, этот навык и `.editorconfig`. Проверить remote URL,
   `git worktree list`, текущую ветку, staged и unstaged изменения.
2. Получить свежую `origin/ufc/cinema-stable`. Не считать локальный cached ref
   свежим без fetch. В этом репозитории origin исторически настроен на fetch
   только stable; для обзора веток указывать полный refspec явно.
3. Создать новую task-ветку от актуальной `origin/ufc/cinema-stable`, а не от
   старой feature-ветки или случайного текущего HEAD. Для параллельных задач
   использовать отдельные worktrees; не переключать ветку чужой рабочей папки.

Пример для новой задачи (путь и имя должны быть свободны):

```powershell
git fetch --no-tags origin '+refs/heads/*:refs/remotes/origin/*'
git worktree add --no-track -b codex/fix-queue-next 'D:/unityhub/worlds/VVMW Tasks/queue-next' origin/ufc/cinema-stable
```

`--no-track` не привязывает новую task-ветку к удалённой production-ветке.
После разрешённого первого push привязывать её к одноимённой ветке origin:

```powershell
git push -u origin codex/fix-queue-next
```

В sparse checkout каталог `.agents/skills/ufc-vizvid-fork` должен входить в
объявленный sparse-набор вместе с нужными исходниками. Одного наличия файлов
на диске недостаточно: при следующем reapply файлы вне набора могут исчезнуть.
Если каталог отсутствует в `git sparse-checkout list`, добавлять его через
`git sparse-checkout add .agents/skills/ufc-vizvid-fork`, сохраняя прежний набор;
не заменять весь набор командой `set` ради одного навыка. Перед изменением правил
проверить чистоту worktree и сохранить нужные материализованные tracked-файлы,
которые лежат вне текущего набора. После изменения `git sparse-checkout check-rules`
для путей SKILL.md и references/workflow.md должен включать оба файла; проверить
также их наличие на диске. Не принимать отсутствие файлов вне sparse-набора за
их удаление из репозитория. Незакоммиченные чужие изменения не прятать и не
заменять ради начала задачи.

Ссылки из навыков Cinema должны вести к навыку в фактическом worktree stable,
который найден через `git worktree list` (сейчас `D:/unityhub/worlds/VVMW Playback Speed`).
Папка общего репозитория `VVMW Source` может быть checkout исторической `main`
с локальной устаревшей копией навыка; она не подменяет production-точку входа.

## Разработка и интеграция

1. Менять исходники в task-ветке. Изменения установленного `Packages` в Cinema
   не заменяют исходник форка. Сохранять package ID, GUID и рабочие UFC-контракты.
2. Делать небольшие законченные коммиты с понятной причиной. Выполнять проверки
   по изменённому поведению: C# и Udon для runtime; native player/queue/retry/
   repeat/clock/mirror проверки по затронутой области. Для сетевого поведения
   отдельно указывать, что проверено двумя VRChat-клиентами, а что было seeded.
   Для одних инструкций достаточно проверки навыка, ссылок и diff.
3. Перед интеграцией снова fetch origin. Если stable ушла вперёд, влить её в
   task-ветку обычным merge, разрешить конфликты и повторить затронутые проверки.
4. Основной путь ревью — PR в `ufc/cinema-stable`: проблема, изменение, проверки,
   ограничения. Соблюдать approval/AI-audit правила `AGENTS.md` и CONTRIBUTING.
   Если пользователь прямо разрешил локальный merge/push без PR, применить тот
   же просмотр diff и проверки; отдельный PR не создавать вместо его запроса.
5. Сливать принятую задачу обычным merge commit (`--no-ff`), сохраняя историю
   задачи. Опубликованную историю и stable не переписывать, force-push не делать.
   Непринятые эксперименты не добавлять попутно.
6. Push выполняется только в разрешённую пользователем ветку origin. После push
   проверять удалённый SHA через `git ls-remote`, а не только local tracking ref.

Рабочую production-ветку обновлять из origin через fast-forward. Если она
разошлась с remote, сначала разобраться в коммитах; не применять reset или
автоматическое разрешение конфликтов ради получения «чистого» состояния.
Срочное исправление тоже начинает `codex/fix-<task>` от текущей stable.

## Обновление из upstream

Обычная цель production-обновления — конкретный официальный release tag.
В оригинальном репозитории сейчас основной HEAD указывает на `develop`;
движущийся `upstream/develop` подходит для исследования и предварительных
проверок, но не выбирается автоматически вместо выпущенной версии.

1. Получить upstream refs и выбранный release tag. Сохранять upstream-теги в
   namespace `upstream/`, чтобы не путать их с нашими release tags. Зафиксировать
   точный commit выбранного тега; изменившийся существующий тег не перезаписывать.
2. Создать `codex/upstream-<version>` от последней `origin/ufc/cinema-stable`.
3. Сделать merge выбранного upstream-тега в эту ветку. Проверить конфликтные
   решения и результат до создания merge commit; не выбирать глобально ours/theirs.
4. Сопоставить каждую UFC-правку с новым upstream: сохранить её, адаптировать или
   убрать только после подтверждения, что upstream решает ту же проблему.
   Это относится к clock, ownership/Stop/retry, repeat/queue и private mirror
   transport. В metadata принять нужные upstream dependencies, сохранив наш ID
   и осмысленную UFC-версию. GUID не пересоздавать.
5. Пройти C#/Udon и регрессии затронутых систем. Если upstream меняет clock,
   заново проверить его поведение и verified hash/gate, а не механически
   закреплять старый hash. Для backend/network изменений провести соответствующее
   native/client тестирование; не объявлять его успешным по одним моделям.
6. Принятый результат влить в `ufc/cinema-stable` через merge commit с сохранённой
   upstream ancestry. Новую stable квалифицировать для установки/выпуска отдельно.

Пример ниже использует условный будущий релиз `1.8.4`, а не утверждает его наличие:

```powershell
git fetch --no-tags upstream
git fetch --no-tags upstream refs/tags/1.8.4:refs/tags/upstream/1.8.4
git worktree add --no-track -b codex/upstream-1.8.4 'D:/unityhub/worlds/VVMW Tasks/upstream-1.8.4' origin/ufc/cinema-stable
# Следующую команду запускать уже в новом worktree:
git merge --no-ff --no-commit refs/tags/upstream/1.8.4
```

Один upstream merge сохраняет происхождение изменений лучше, чем перенос всей
новой версии россыпью cherry-pick. Для отдельного срочного upstream-исправления
допустим целевой cherry-pick в task-ветку с указанием исходного SHA; перед ним
проверить зависимости, а при последующем полном обновлении — эквивалентность.

## Версия, выпуск и установка

Git SHA, имя ветки, версия package.json и опубликованный VPM archive — разные
идентификаторы. Например, `1.8.3-cinema.6` — версия пакета.

Для выпуска создать release-ветку от принятой stable, согласовать версию пакета
и changelog, собрать и проверить точный кандидат. После принятия merge обратно
в stable; release tag и архив должны соответствовать одному принятому source SHA.
Наши теги имеют префикс `ufc-`, upstream-теги — `upstream/`; существующие
опубликованные теги и архивы не переименовывать и не заменять.

Source push, публикация VPM listing/archive, установка пакета в Cinema и VRChat
world upload — отдельные действия в рамках соответствующего запроса пользователя.
При установке использовать проверенный кандидат и защищённый путь импорта,
сохранив GUID и несохранённую сцену. Generated Udon outputs не подменяют исходники.
Откат принятого source-изменения делать новым revert commit; откат установленного
пакета — на известную версию/снимок, сохраняя текущую авторскую сцену.

## Состояние текущей задачи

В отчёте указывать имя task-ветки и worktree, base stable SHA, свои commit SHA,
результаты проверок, target stable SHA после интеграции и факт remote-проверки
после push. Если commit, merge, push или релиз не выполнялись, говорить об этом
прямо. Это позволяет отличать готовое локальное исправление от опубликованного.

Первичные справочники для Git-команд:
[worktree](https://git-scm.com/docs/git-worktree),
[fetch](https://git-scm.com/docs/git-fetch),
[merge](https://git-scm.com/docs/git-merge).
